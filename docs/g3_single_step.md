# G3 单步对账与 S17 五项验收门

Phase 1 在 commit 0016（`aa84a31`）之上的最终答卷。代码与 120 组 GPU 基线不变；这里入库的是 8 die 单步切分的物理证据，以及由它给出的 S17 验收门。

配套文件：

- [`g3_single_step.json`](g3_single_step.json)：切分原始数据（11 段设备时间）
- [`../../scripts/g3_steps.py`](../../scripts/g3_steps.py)：切分脚本（按 `ArgMaxV2` 划界、按实测算子名归类）

口径：一步之内所有下发的 Task Duration 之和，按类归并。这是设备上真正执行的时间，与 wall 之间的差是主机气泡，单列不摊。表 3a 取稳态 prefill 段（段 2）；JSON 顶层 `prefill` 是脚本对三段 prefill 的均值（739.86 ms），**不要用那个均值代替表 3a**。

## 边界算子由数据给出，不预设

不假设叫什么，而是问「哪些算子出现次数像是每步一次」：

```
ArgMaxV2        11 次
GreaterEqual    11 次
GatherV2        11 次
ReduceMean      11 次
LogicalAnd      11 次
```

五个同频，是采样链路。取 `ArgMaxV2` 作边界，4531 ms 轨迹切成 11 段。

## 切对了的证据：decode 7 步彼此一致

| 段 | 身份 | 下发 | 设备 ms | 墙上 ms |
|---|---|---|---|---|
| 0 | prefill S=1024 | 4069 | 667.70 | 1585.84 |
| 1 | prefill S=1024 | 4058 | 1059.72 | 1959.03 |
| 2 | **prefill S=1024（稳态）** | 4103 | **492.15** | 410.08 |
| 3–9 | decode B=16 | ~1850 | **48.71–55.27** | 32–45 |

decode 7 步极差 **11.9%**——这个一致性本身就是切对了的证据，按时间等分永远得不到。

**prefill 取段 2 而非三段均值。** 段 0/1 每一类都等比例放大（段 1 ≈ 段 2 的 2 倍，各类一致），说明不是某个算子异常，是还含 warmup/编译；而且两段的墙上时间远超设备时间（1586 vs 668），同样印证。段 2 墙上 410 < 设备 492（多流并发），才是稳态形态。

## 表 4：误差归因

**(a) 通信被严重低估，是最大的一项。** prefill 26.0×、decode 21.9×。集合通信的 provider 是「注册但禁用」（单进程测不了一组卡），全部落回 `t_sol` 上界；而实测里每个 `hcom_*` 还**带一个 AICPU 伴随核**（`allreduceAicpuKernel` 等），模型里完全没有这个实体。

**(b) 注意力预测为 0，是签名缺口不是建模误差。** GLM 实际跑 `SparseFlashAttention` 与 `ChunkKdaFwd`，Ascend 侧这两个都没有 provider（S14.5 已记录），预测侧这一类的 `t_sol` 是 0。

**(c) 超连接 12.0% / 7.2% 完全未建模。** `HcPre` + `HcPost` 是 GLM 超连接的下发开销，**HuggingArch 的六个类里没有对应类**，预测为 0。全新发现。

**(d) MoE 路由：S15 的假设被证实。** decode 下预测 10.60 ms、实测 **5.19 ms**——**预测是实测的 2 倍**。S15 曾观察到「decode 预测高估 batch 敏感度」（B1→B16 预测涨 178%、实测仅 28%）并明确标注为假设，现在逐类设备时间正式证实：模型假定专家权重访存随激活专家数增长，而 `GroupedMatmulSwigluQuant` 实际读取接近固定的一组专家。

**这是唯一预测偏高的一类，其余全部偏低。**

实测覆盖的只有 `gemm`、`moe_grouped_matmul`、`norm_act` 三类，合计约 22% 的设备时间。占比最大的三块——通信 41.8%、注意力 17.5%、超连接 12.0%——全部没有覆盖。「910C 算子实测完成」这个说法不成立。

## 方法论

**归类必须读实测算子名。** 第一版按常见命名猜（`HcclAllReduce`、`FusedInferAttentionScore`、以为矩阵只有 `MatMulV3`），`other` 占 84%；按真实名字（`hcom_allReduce_` + `allreduceAicpuKernel`、`SparseFlashAttention` / `ChunkKdaFwd`、INT8 另有 `QuantBatchMatmulV3`）重归后降到 10.5%。

**比占比，不比绝对值，除非口径已对齐。** 整次 generate 的 4531 ms 对单步 89.29 ms 是 51×，看起来模型错得离谱；切到单步后 prefill 5.5×、decode 3.2×，而且差距集中在三个可命名的类上。口径不齐时「倍数」没有意义。

**离线补解析曾被证伪，挂卡后 4 秒成功。** `msprof --export` 报 `Init platform by driver failed!`——它需要驱动初始化平台，不是纯 CPU。挂单颗 Die 0 后一次成功。

## S17：五项验收门

S14.5 与 S16 把「测得出、读得到」这条链打通了，但表 3 证明实测只覆盖约 22% 的设备时间，最大的三块都没覆盖。以下五项各自独立，按影响面排序。每项都要先做**影响面 dry-run** 再落代码（S16 的做法：量出状态跃迁矩阵，确认零次反向翻转），并配一个**回退时会红**的 oracle。

架构改动不在 `ascend-910c` 的 0016 封版上做，而在 `ascend-910c-s17-arch` 上进行。

### S17a 注意力签名（表 3 的 17.5% / 3.0%）

- **缺口**：GLM 走 `kda`（37 cell）与 `per_head_gemm`（104 cell），Ascend 侧均无 provider；既有的 `gqa_attention` provider GLM 走不到。
- **验收门**：两个 provider 注册并通过对拍；GLM 目标布局下 attention 类预测从 0 变为非 0，与实测 86.00 ms（prefill）同量级。
- **前置**：`kda` 的参考实现需确认存在（`refs.py` 已有 `kda` 签名）。

### S17b 集合通信（表 3 的 41.8% / 50.3%，最大一项）

- **缺口**：provider「注册但禁用」，单进程测不了一组卡；且实测每个 `hcom_*` 带一个 AICPU 伴随核，模型中无此实体。
- **验收门**：多进程采集通路跑通，16 die allreduce/alltoall 实测入库；伴随核的归属在代价模型中有声明（算进通信，还是单列）。
- **风险**：需改 harness 的单进程模型——S11 曾明确拍板不改，**重开此项等于推翻那次决定，需先确认**。

### S17c 超连接计价（表 3 的 12.0% / 7.2%，全新发现）

- **缺口**：`HcPre` + `HcPost` 占单步 prefill 12%，HuggingArch 六个类里**没有对应类**，预测为 0。
- **验收门**：表 3 补一类；`hyper_connection` 的下发开销在代价模型中有公式；GLM 预测的该类 t_sol 与实测 59.10 ms 同量级。

### S17d BF16 gemm provider（462 cell，量最大但技术最简单）

- **缺口**：Ascend 的 `gemm` provider 只服务 INT8，462 个 BF16 cell 无人接。
- **验收门**：BF16 gemm provider 通过对拍；该布局下 `gemm` 类命中数从当前的 3 升到覆盖多数 cell。

### S17e 页大小导出 + 条件槽位（两个小而硬的）

- **页大小**：vLLM 把 GLM 的 128 改成 640（`patch_mamba_config.py:139`），而 binding 按常量声明。**直接改常量会让已有 54 行 Qwen/Llama 语料键错**——必须先做影响面 dry-run（方法同 S16）。**验收门**：页大小按 (框架, 模型缓存结构) 导出；54 行既有语料的键不变。
- **条件槽位**：`quantise_activation` 的 binding 条件命名了错误的槽位（int8 在**输出**槽，激活槽是宽 bf16），需扩 `DispatchCondition.KEYS` 闭世界词表。**验收门**：该 op 的 2 行实测被估算读到。
